# AI / LLM Plan v2

## 1. Objective

Add LLM capability to AI Sales Agent in a way that is:

* reliable under production conditions
* safe for operator workflows
* observable and debuggable
* cost-bounded
* reversible by feature flag
* non-destructive when the model fails

The LLM should improve speed, clarity, and operator leverage. It must not become an untrusted decision engine that silently mutates CRM state.

---

## 2. Core Operating Principles

### 2.1 LLM is assistive first

The model may:

* generate text
* summarize context
* classify or score with explanation
* recommend next actions
* suggest routing, quote, or pipeline actions

The model may **not** directly perform destructive or state-changing actions without deterministic approval logic and explicit execution flow.

### 2.2 Deterministic fallback is mandatory

Every LLM-backed feature must have:

* a deterministic fallback path
* a stable response contract
* a visible fallback indicator in UI
* a logged fallback reason

If the model fails, the product must degrade gracefully, not break.

### 2.3 Schema validity is necessary but not sufficient

A valid JSON payload does **not** automatically mean the result is trustworthy.

Each feature must validate:

* schema shape
* business completeness
* contradiction checks
* confidence threshold or fallback rules

### 2.4 Human review remains authoritative

For any action affecting:

* lead ownership
* deal stage
* quote readiness
* discount guidance
* margin safety
* automation reruns
* SLA escalation

The operator remains the final authority unless a future explicit policy says otherwise.

---

## 3. Decision Boundary Matrix

### 3.1 LLM-only output allowed

These can be generated by LLM and shown directly if schema/business validation passes:

* copilot text responses
* reply drafts
* clarification questions
* triage summaries
* lead reasoning
* quote summaries
* remediation hints
* next-best-action explanations

### 3.2 LLM recommendation only

These may be suggested by the model but require deterministic review / operator confirmation:

* assign owner
* move stage
* mark stalled / high risk
* approve discount range
* margin safety recommendation
* routing suggestion
* SLA escalation suggestion
* automation rerun recommendation

### 3.3 Deterministic system of record

These must remain deterministic even if the model participates upstream:

* permission checks
* pagination
* final execution logging
* activity writes
* workflow rerun guardrails
* quote creation blocking conditions
* required-field checks
* state transition authorization

---

## 4. Runtime Architecture

### 4.1 Shared LLM runtime service

Create one shared runtime layer responsible for:

* provider selection
* model selection
* prompt template loading
* system prompt injection
* feature prompt versioning
* request timeout handling
* retry policy
* schema parsing
* fallback dispatch
* observability event writing

Suggested internal interface:

```ts
def runAiFeature({
  feature,
  input,
  schema,
  fallback,
  timeoutMs,
  maxInputChars,
  maxOutputTokens,
  temperature,
}) {}
```

### 4.2 Provider abstraction

Support provider abstraction from day one even if only one provider is enabled initially.

Provider interface should normalize:

* model name
* latency
* usage/tokens
* raw text
* parsed payload
* error classification

### 4.3 Prompt template registry

Store prompts per feature:

* copilot.query
* triage.lead
* reply.first
* reply.followup
* reply.questions
* quote.recommendation
* quote.copilot
* pipeline.insights
* automation.remediation
* routing.sla

Each prompt should have:

* feature key
* version
* input contract
* output contract
* business notes

## 5. Validation Pipeline

Every LLM feature must pass this pipeline:

1. input normalization
2. context trimming / token budget enforcement
3. provider call
4. raw response capture
5. JSON extraction / parse
6. schema validation
7. business validation
8. contradiction / trust checks
9. fallback if needed
10. UI + audit output

### 5.1 Business validation examples

#### Reply Studio

Reject or fallback if:

* message is empty
* subject required for email but missing
* clarification mode has no questions
* output contradicts known lead context

#### Quote Recommendation

Reject or fallback if:

* no recommendation lines
* suggested quantity is nonsensical
* variant conflicts with known lead data
* missing-data list contradicts canCreateQuote

#### Pipeline Insights

Reject or fallback if:

* risk score exists without reasons
* urgency queue empty when stalled is true
* next action missing
* stage aging / inactivity numbers invalid

#### Quote Intelligence

Reject or fallback if:

* discount band exists without rationale
* margin status exists without reasons
* output suggests approval where required fields are missing

---

## 6. Parse Failure Policy

### 6.1 Hard failure categories

Trigger fallback immediately if:

* no response
* timeout
* invalid JSON
* schema invalid
* required business fields missing
* contradictory payload
* provider unavailable

### 6.2 Soft failure categories

Allow result but mark reduced trust if:

* low-confidence wording
* weak rationale
* vague output
* over-generic advice
* missing optional detail

Soft failure should surface as:

* “validated, low confidence”
* “fallback not used, but human review recommended”

---

## 7. Cost and Latency Controls

### 7.1 Per-feature budgets

Define per-feature limits:

* max input chars
* max output tokens
* timeout ms
* retry count
* concurrency cap

Example policy:

* copilot.query: medium context, low retries
* reply studio: small context, fast timeout
* quote copilot: medium context, strict validation
* pipeline insights: small context, deterministic-friendly
* quote intelligence: small context, deterministic-first

### 7.2 Daily and monthly controls

Add:

* daily token budget
* daily spend budget
* provider kill switch
* per-feature disable flag
* per-environment cap

### 7.3 Timeout policy

If timeout occurs:

* do not keep spinner indefinitely
* return fallback with visible note:

  * “Primary model timed out. Deterministic fallback used.”

## 8. Feature Flag and Rollout Matrix

### 8.1 Flags

Add flags per feature:

* ai_runtime_enabled
* ai_copilot_live
* ai_triage_live
* ai_reply_studio_live
* ai_quote_recommendation_live
* ai_quote_copilot_live
* ai_pipeline_insights_live
* ai_quote_intelligence_live
* ai_automation_hints_live
* ai_routing_sla_live

### 8.2 Rollout stages

#### Stage 0 — local only

* dev testing
* contract validation
* prompt iteration
* no production traffic

#### Stage 1 — staging dark launch

* feature enabled
* visible only to internal admins
* compare LLM vs fallback outputs
* no operator trust assumption yet

#### Stage 2 — production dark launch

* production traffic sampled
* LLM runs in background
* UI still shows deterministic result
* compare quality and latency

#### Stage 3 — flagged operators

* selected admin/sales_manager users
* visible trust labels
* monitor errors, latency, fallback rate

#### Stage 4 — wider rollout

* role-based expansion
* per-feature enablement
* kill switch preserved

### 8.3 Role gating

Suggested rollout priority:

* admin
* sales_manager
* ops
* sales_rep

Do not start with sales_rep first. Start with the people who can spot bad output.

## 9. Observability and Audit

For every AI request, log:

* feature
* prompt version
* prompt hash
* provider
* model
* latency ms
* token usage if available
* schema_valid
* business_valid
* fallback_used
* fallback_reason
* confidence
* request id
* related lead/deal/quote ids
* user id / role
* environment

### 9.1 Audit separation

Keep two layers:

#### AI runtime logs

Technical debugging:

* model
* latency
* prompt version
* parse status

#### Activity / business logs

Operator-facing record:

* what was generated or recommended
* whether fallback was used
* whether an action was executed
* execution outcome

---

## 10. UX Trust Rules

Every AI surface must show:

* provider or “deterministic”
* source: primary vs fallback
* validated output indicator
* latency state while running
* human review note where relevant

### 10.1 Sensitive action rule

For features affecting business state, show:

* “AI suggested”
* “Human confirmation required”

Apply this to:

* stage move suggestions
* owner assignment
* quote readiness
* discount guidance
* rerun actions
* routing escalation

### 10.2 Empty and fallback copy

Do not use vague messages.

Use explicit messages like:

* “Primary model timed out. Deterministic fallback used.”
* “Output passed schema validation but requires human review.”
* “Missing business fields prevented AI recommendation. Fallback used.”

## 11. Execution Roadmap

### Phase 1 — Shared Runtime Foundation

Build:

* provider abstraction
* feature registry
* prompt registry
* schema parser
* fallback wrapper
* logging layer
* token/timeout limits
* feature flags

Exit criteria:

* one runtime function can safely run one feature with fallback and logs

### Phase 2 — High-Visibility AI Features

Enable live LLM for:

* copilot query
* lead triage
* reply studio

Reason:
These create immediate AI feel with low destructive risk.

Exit criteria:

* fallback rate acceptable
* latency acceptable
* operators trust output enough to use it

### Phase 3 — Commercial Guidance Features

Enable live LLM for:

* quote recommendation
* quote copilot summary
* pipeline insights

Keep deterministic approval rules for:

* canCreateQuote
* critical missing-data detection
* stage risk thresholds where needed

Exit criteria:

* no hallucinated commercial outputs passing validation
* quote logic remains controllable

### Phase 4 — Safety-Critical Guidance

Enable LLM-assisted, not LLM-authoritative logic for:

* quote intelligence
* smart routing + SLA
* automation remediation hints

These must remain recommendation-first until enough evidence exists.

Exit criteria:

* strong audit visibility
* stable trust labels
* low contradiction rate

### Phase 5 — Automation and Orchestration Expansion

Add:

* automation template generation suggestions
* failure remediation suggestions
* lead-to-close orchestration memory
* multi-step AI guidance flows

## 12. Per-Feature Rules

### 12.1 Copilot

LLM can:

* answer
* summarize
* suggest actions

LLM cannot:

* execute destructive actions directly

### 12.2 Triage

LLM can:

* classify
* summarize
* explain urgency / complexity

Deterministic checks:

* required fields
* score bounds
* fallback if weak output

### 12.3 Reply Studio

LLM can:

* draft first reply
* draft follow-up
* ask clarification questions
* rewrite tone

Deterministic checks:

* output completeness
* channel compatibility
* required structure

### 12.4 Quote Recommendation

LLM can:

* recommend products
* infer quantity or variant from text
* explain rationale

Deterministic checks:

* missing data
* blocking conditions
* quote readiness

### 12.5 Quote Copilot

LLM can:

* generate quote summary
* suggest upsell/cross-sell

Deterministic checks:

* accepted recommendations required
* no quote-ready state if blocking missing data exists

### 12.6 Pipeline Insights

LLM can:

* explain risk
* generate next-best-action narrative
* summarize urgency

Deterministic checks:

* stage aging
* inactivity
* stalled thresholds

### 12.7 Quote Intelligence

LLM can:

* explain margin risk
* suggest discount band rationale

Deterministic checks:

* margin safety floor
* missing field blocks
* explicit review requirement

### 12.8 Smart Routing + SLA

LLM can:

* explain routing logic
* explain SLA urgency
* suggest next action

Deterministic checks:

* final routing eligibility
* final SLA bucket logic if used operationally

---

## 13. Reliability Acceptance Criteria

A feature is not considered production-ready until it meets all of these:

* schema validation success rate acceptable
* fallback path verified
* timeout behavior verified
* audit logs written consistently
* UI trust labels visible
* deterministic guardrails still authoritative
* operator can understand why a result appeared
* kill switch tested

---

## 14. Open Questions to Resolve Before Full Rollout

* Which provider/model combination is primary for each feature?
* What token limits apply per feature?
* What is the acceptable fallback rate per feature?
* Which features are allowed for sales_rep first?
* What is the monthly spend cap?
* What contradiction rate is tolerated before rollback?
* Which actions remain forever “recommendation only”?

---

## 15. Final Implementation Position

This system should be built as:

* **LLM-assisted**
* **deterministically guarded**
* **feature-flagged**
* **observable**
* **operator-transparent**
* **rollback-ready**

Not as “let the model run the CRM.”
